# 塔防类产品外挂治理搭建流程

> 适用范围：后续塔防类产品通用外挂治理框架。具体阈值不得跨项目直接复用，必须经过新项目埋点验收、分布观察和异常样本复盘后确定。

## 一、总体闭环

**外挂埋点设计 → 埋点验收与整体分布观察 → 治理看板与试检测 → 封禁机制 → 效果复盘与规则迭代**

目标是形成：**可发现 → 可验证 → 可检测 → 可处置 → 可复盘** 的治理闭环。

## 二、阶段1：外挂埋点设计

1. **按玩法拆分风险**
   - 主线 PVE、Boss、竞技、无尽、特殊活动等需要分别评估。
   - 不建议用同一阈值覆盖所有玩法。

2. **与开发、策划定义异常数据**
   - 先明确正常情况下“不可能发生”的数据，再明确“极低概率异常”的数据。
   - 优先从战斗公式、服务端约束、数值上限和操作频率中找异常点。

3. **客户端 / 服务端双端埋点**
   - 对关键数据尽量同时记录客户端值和服务端值，用差异进行校验。
   - 典型字段：城墙生命、怪物生命、伤害、操作次数、战斗结果、战斗持续时间等。

4. **定位字段必须完整**
   - 角色ID、区服ID、Battle UID、玩法类型、关卡/Boss ID、战力、事件时间、版本、渠道、创角时间等。
   - 保证异常可以还原到具体玩家、具体玩法、具体单局。

## 三、阶段2：埋点验收与整体分布观察

1. **埋点验收**
   - 检查触发时机、字段类型、空值、取值范围。
   - 校验客户端/服务端字段是否在同一 Battle UID 下可比较。

2. **整体分布观察**
   - 先看全量分布和分组分布，再定阈值。
   - 建议观察 P50 / P90 / P95 / P99、极值、样本量，并按玩法、战力、成长天数、版本等拆分。

3. **人工抽样复盘**
   - 将异常样本还原到具体战斗。
   - 区分：真实外挂、埋点 Bug、数值边界、正常极端玩家。

4. **形成初版规则**
   - 硬规则：正常逻辑下明确不可能发生。
   - 统计规则：Z-score、分位数、倍率异常等。
   - 组合规则：多指标共同命中。

## 四、阶段3：治理看板与试检测

1. **治理看板建议字段**
   - 异常人数、异常次数、异常类型、玩法、版本、渠道、区服、累充、战力、首次异常时间、最后异常时间。
   - 支持异常玩家明细下钻和单局证据查看。

2. **先试检测、不立即封禁**
   - 初版规则先只做标记。
   - 连续观察误报率、异常复现率、规则命中重合度。

3. **异常风险分层**
   - 高危：硬规则命中、多规则命中、短时间反复命中。
   - 中危：统计异常持续复现。
   - 低危：单次边缘异常。

4. **动态迭代**
   - 版本更新、数值成长、玩法调整后，需要重新检查异常分布和阈值有效性。

## 五、阶段4：封禁机制与长期闭环

1. **封禁策略**
   - 明确：直接封 / 人工复核 / 观察名单。
   - 封禁必须保留可解释证据链。

2. **处置机制**
   - 自动封禁、人工复核、客服申诉、解封、证据留档。

3. **效果评估**
   - 外挂率、误封率、复发率、申诉成功率、版本前后异常率。

4. **前置到新玩法流程**
   - 新玩法评审时同步评估外挂风险和埋点需求。
   - 上线前完成埋点设计，上线后完成验收、观察、规则上线和看板监控。

## 六、现有项目可复用的异常信号参考

来自现有 `battle_check` / `boss_battle_result` 治理经验，仅作为设计参考：

- 客户端城墙最大生命 vs 服务端城墙最大生命差异。
- 客户端怪物生命 vs 服务端怪物生命差异。
- 局内刷卡/刷新等操作次数超过合理上限。
- PVE 耗时按战力、成长天数、玩法、关卡分组后做 Z-score / 分位数异常。
- Boss 伤害按战力、Boss、赛季/周期分组计算高分位后，再观察异常倍率。
- 后续塔防产品建议补充：攻击/技能频率异常、资源生成异常、战斗结果不一致、移动/位置异常（如玩法存在移动机制）、多规则复合风险。

## 七、核心原则

- **先业务逻辑，后阈值。**
- **先验收和观察，后正式封禁。**
- **硬规则优先，统计规则必须有样本量与分组控制。**
- **任何封禁规则都应支持回溯到玩家和具体战斗证据。**
- **外挂治理需要随版本长期维护，不能一次性建设后固定不变。**
