# 下方了项目表口径

更新时间：2026-08-28

- 下方了项目使用数数 41 项目表。
- 用户表：ta.v_user_41。
- 事件表：ta.v_event_41。
- 后续涉及下方了项目 SQL，默认不要使用 44，优先使用 41。
- ta.v_user_41 没有 first_payment 字段；首日付费分层必须使用注册当天 pay_log.payment 汇总。
- pay_log.payment 单位为分，统计金额和首日付费分层前必须除以 100 转为元。
- 主线战斗开始事件为 battle_star，不是 battle_start；主线战斗用 battle_type = 1。
- 次日留存或流失判断可按次日是否存在 in_out_log 事件。
- 数数看板日期变量 PartDate date 已经自带分区日期字段条件时，不能在前面再拼分区日期字段，否则会展开成重复字段名并报错。
- 当前下方了看板 SQL 中，事件表日期筛选直接单独写日期变量；次日日期范围也直接单独写次日日期变量。
- 如果要筛选 create_role_time 转换得到的新增日期，不要直接把日期宏拼接在派生字段上，改用事件表分区日期与新增日期关联，或使用明确的起止日期参数。
- 下方了 LTV 观察截止日期固定取昨天，统一使用 `date_add('day',-1,date(now()))`，不再使用 `${Variable3}`。
- 流失名单 SQL 中的“是否滚服”表示当前角色是否为滚服而来的角色：以当前角色 `cr` 的 `nb_open_id` 关联同一 `nb_open_id` 下更早创建的其他角色；若存在 `old_role.create_role_time < cr.create_role_time` 的老角色，则当前角色标记“是否滚服=是”。
- 因此“是否滚服=是”描述的是玩家进入当前角色/当前服之前已有老角色经历，不代表当前角色流失后又去了别的服务器，也不能据此把当前角色流失判断为“假流失”。

## 跨渠道收入/活跃分析口径（2026-08-28）
- 跨渠道玩家唯一标识统一使用 `nb_open_id`，不再使用 `open_id` 兜底逻辑。
- 行为渠道取事件当天实际 `channel_id`；最初渠道取同一 `nb_open_id` 下 `create_role_time` 最早角色的 `channel_id`。
- `tag`：最初渠道=行为渠道记为“纯新”；最初渠道<>行为渠道记为“自有新增”。
- 渠道新增玩家：同一 `nb_open_id` 首次在该行为渠道出现 `in_out_log` 的当天。
- 下方了渠道映射：3056220=支付宝小游戏；3056219=官方Android渠道直播投放包；3056215=官方Apple渠道；3056214=抖音小游戏；3056211=微信小游戏；3056210=官方Android渠道。
- 微信大盘渠道池：3056211、3056210、3056215、3056219；排除抖音小游戏 3056214 和支付宝小游戏 3056220。
- 下方了无小黄车收入口径；普通内购不限制 `change_reason`，不限制 `pay_result`，仅要求 `payment>0`，金额 `/100` 转元。
- 该跨渠道报表不使用 `${Time:time1}` 动态时间筛选；查询可保留明确的固定历史起点用于控制扫描范围和首次渠道判定。
- 性能优化原则：`in_out_log` 先压缩至“日期×nb_open_id×channel_id”；`pay_log` 先聚合至“日期×nb_open_id×channel_id”；首次渠道日期使用 `GROUP BY + MIN`，最初渠道使用 `min_by(channel_id, create_role_time)`，避免大范围窗口函数与明细 JOIN 膨胀。
