# 下方了项目表口径

更新时间：2026-08-20

- 下方了项目使用数数 41 项目表。
- 用户表：ta.v_user_41。
- 事件表：ta.v_event_41。
- 后续涉及下方了项目 SQL，默认不要使用 44，优先使用 41。
- ta.v_user_41 没有 first_payment 字段；首日付费分层必须使用注册当天 pay_log.payment 汇总。
- pay_log.payment 单位为分，统计金额和首日付费分层前必须除以 100 转为元。
- pay_log 有效付费可按 `coalesce(payment,0) > 0 OR coalesce(token_payment,0) > 0` 判断；需要统计含代金券金额时，金额口径使用 `(coalesce(payment,0) + coalesce(token_payment,0)) / 100`。
- 首日首次付费项目留存分析：首付项目取创角当天第一笔有效 pay_log；如果该第一笔的 product_type='直充'，则该玩家整体剔除，不把后续第二笔重新认定为首付。
- 2日内月卡口径：创角当天+D2（新增后第1个自然日）内，有效 pay_log 的 product_type 或 product_name 包含“月卡”即记为“2日内买月卡”。
- 二次付费玩家口径：为避免未来信息反向筛选留存，若用于“前两日付费金额分层 × D2-D7留存”，二次付费统一定义为创角前两日（D1+D2）内至少发生2笔有效 pay_log；前两日付费金额按 `(payment + token_payment) / 100` 累计。
- 前两日付费金额分层沿用常用档位：b_(0,6]、c_(6,30]、d_(30,100]、e_(100,300]、f_(300,500]、g_(500,1000]、h_1000+。
- 主线战斗开始事件为 battle_star，不是 battle_start；主线战斗用 battle_type = 1。
- 次日留存或流失判断可按次日是否存在 in_out_log 事件。
- `ta.v_event_41.create_role_time` 当前可能为 double，不能直接写 `date(create_role_time)`；留存等按新增日计算的 SQL 应优先从 `ta.v_user_41.create_role_time` 取得新增日期，再与事件表 `#event_time` 做 `date_diff`。
- 数数看板日期变量 PartDate date 已经自带分区日期字段条件时，不能在前面再拼分区日期字段，否则会展开成重复字段名并报错。
- 当前下方了看板 SQL 中，事件表日期筛选直接单独写日期变量；次日日期范围也直接单独写次日日期变量。
- 如果要筛选 create_role_time 转换得到的新增日期，不要直接把日期宏拼接在派生字段上，改用事件表分区日期与新增日期关联，或使用明确的起止日期参数。
- 下方了 LTV 观察截止日期固定取昨天，统一使用 `date_add('day',-1,date(now()))`，不再使用 `${Variable3}`。
- 流失名单 SQL 中的“是否滚服”表示当前角色是否为滚服而来的角色：以当前角色 `cr` 的 `nb_open_id` 关联同一 `nb_open_id` 下更早创建的其他角色；若存在 `old_role.create_role_time < cr.create_role_time` 的老角色，则当前角色标记“是否滚服=是”。
- 因此“是否滚服=是”描述的是玩家进入当前角色/当前服之前已有老角色经历，不代表当前角色流失后又去了别的服务器，也不能据此把当前角色流失判断为“假流失”。
